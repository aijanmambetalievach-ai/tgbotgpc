# Tender Bot — Telegram-бот для внутренних закупок

Закрытый Telegram-бот для тендерного отдела: сотрудник создаёт закупки,
выбирает закупщиков, получает от них заявки со списками товаров, выгружает
Excel (индивидуальный и сводный) и управляет статусами. Закупщики видят только
те закупки, к которым их подключили, и подают заявки свободным текстом —
детерминированный парсер превращает его в структурированные позиции.

## Возможности

**Сотрудник тендерного отдела (`TENDER_EMPLOYEE`)**

- добавление закупщиков — одноразовой пригласительной ссылкой или по Telegram ID;
- блокировка, разблокировка и отзыв доступа (без физического удаления данных);
- создание закупки двумя способами: пошаговый мастер и «⚡ быстро текстом»;
- выбор участников (поштучно с пагинацией или «все активные закупщики»);
- предпросмотр перед публикацией — автопубликации не бывает никогда;
- список закупок с фильтрами, карточка закупки, участники, статистика;
- входящие заявки, смена статусов, обязательная причина при отклонении;
- индивидуальный и сводный Excel;
- продление дедлайна (с записью в audit log) и напоминание не ответившим.

**Закупщик (`PURCHASER`)**

- список доступных ему активных закупок;
- подача заявки по объявленной закупке;
- **своя заявка по собственной инициативе** — без закупки: указывает тему,
  список товаров и отправляет сотруднику тендерного отдела на подтверждение;
- список товаров текстом одним сообщением **или файлом Excel (.xlsx)**;
- шаблон Excel по кнопке «📄 Шаблон Excel»;
- предпросмотр с возможностью исправить, удалить или добавить позицию;
- комментарий к заявке;
- «Мои заявки» и «История», уведомления о смене статуса;
- выгрузка собственной заявки в Excel.

`ADMIN` — системная роль-надмножество `TENDER_EMPLOYEE`; используется для
операций над самими сотрудниками.

## Архитектура

Модульный монолит с однонаправленным потоком зависимостей:

```
Telegram (aiogram handlers, keyboards, FSM)   FastAPI (health / future admin)
                    │                                     │
                    └──────────────► Application services ◄┘
                                            │
                                        Domain (rules, RBAC, transitions,
                                                units, text, time)
                                            │
                                       Repositories (SQL)
                                            │
                                   PostgreSQL / SQLAlchemy async
```

Ключевые правила, заложенные в код:

| Правило | Где обеспечивается |
|---|---|
| Хендлеры тонкие — только парсинг ввода и рендер | `app/bot/handlers/*` |
| RBAC проверяется на сервере, а не «скрытой кнопкой» | `app/domain/permissions.py`, вызовы `require_permission` в каждом сервисном методе |
| Переходы статусов валидируются в домене | `app/domain/transitions.py` |
| Транзакция → commit → только потом уведомления | сервисы коммитят, `NotificationService` вызывается после |
| Ошибка доставки Telegram не откатывает бизнес-операцию | `NotificationService` ловит `TelegramAPIError` |
| Никаких naive datetime | `app/domain/timeutils.py`, все колонки `TIMESTAMPTZ` |
| Парсер подменяем без правки бизнес-логики | `PurchaseListParserProtocol`, `ProcurementParserProtocol` |

Redis намеренно не используется: бот работает одним процессом, FSM хранится в
памяти, анти-спам — sliding window в памяти. Точки расширения описаны в
[Известных ограничениях](#известные-ограничения).

## Доменная модель

```
Procurement (закупка)
├── procurement_participants  (M:N с users — состав фиксируется при публикации)
└── PurchaseRequest (заявка, 1 закупщик = не более 1 заявки на закупку)
    ├── PurchaseRequestItem (позиция: имя, Decimal-количество, единица)
    └── StatusHistory (append-only история статусов)
```

Заявка бывает двух видов:

| Вид | `procurement_id` | `subject` | Кто инициирует |
|---|---|---|---|
| По закупке | заполнен | пусто | сотрудник объявляет закупку, закупщик отвечает |
| Инициативная | `NULL` | тема от закупщика | закупщик, отправляет сотруднику на подтверждение |

Ограничение `UNIQUE(procurement_id, purchaser_id)` работает для обоих: PostgreSQL
считает `NULL` различными, поэтому «одна заявка на закупку» соблюдается, а
инициативных заявок может быть сколько угодно. Check-constraint
`procurement_id IS NOT NULL OR subject IS NOT NULL` не даёт появиться заявке
«ни о чём». Инициативные заявки не попадают в сводный Excel и статистику
конкретной закупки — они к ней не относятся.

Плюс `users`, `invites`, `audit_logs` и `number_counters`.

**Статусы закупки:** `DRAFT → OPEN → CLOSED → COMPLETED`, из `DRAFT`/`OPEN`
возможна отмена, из `CLOSED` — повторное открытие (нужно при продлении срока).

**Статусы заявки:** `DRAFT → SUBMITTED → VIEWED → IN_PROGRESS → COMPLETED`,
из любого рабочего — `REJECTED` (обязательна причина) или `CANCELLED`.

**Номера.** `TENDER-2026-000001` и `REQ-2026-000001` выдаёт таблица
`number_counters` одним атомарным `INSERT … ON CONFLICT DO UPDATE … RETURNING`:
PostgreSQL держит блокировку строки, поэтому одинаковые номера невозможны даже
при параллельных запросах (`max(id)+1` не используется).

## Настройка бота в BotFather

1. В Telegram откройте [@BotFather](https://t.me/BotFather) → `/newbot`.
2. Задайте имя и username (должен заканчиваться на `bot`).
3. Скопируйте токен в `BOT_TOKEN` в `.env`. **Токен не коммитить.**
4. Рекомендуется `/setprivacy` → `Enable` (бот не читает чужие сообщения в группах).
5. Полезно задать команды: `/setcommands`

   ```
   start - Начало работы
   help - Помощь
   cancel - Отменить текущее действие
   ```

Пригласительные ссылки вида `https://t.me/<bot_username>?start=<code>` бот
формирует сам — username подтягивается из API.

## Первый сотрудник тендерного отдела

1. Узнайте свой Telegram ID (например, через `@userinfobot`).
2. Пропишите его в `.env`:

   ```env
   BOOTSTRAP_ADMIN_TELEGRAM_IDS=123456789
   ```

3. Запустите приложение — при старте ID будет создан в таблице `users` с ролью
   `TENDER_EMPLOYEE` (операция идемпотентна и попадает в audit log).
4. Отправьте боту `/start`.

После этого авторизация полностью управляется базой: переменная нужна только
для первичной инициализации и восстановления доступа, если сотрудника случайно
заблокировали. Всех остальных пользователей добавляет сотрудник из интерфейса.

## Локальный запуск без Docker

Docker для разработки **не требуется** — нужен только Python 3.12+ и PostgreSQL.

```bash
python -m venv .venv
source .venv/bin/activate           # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt # только рантайм: requirements.txt

cp .env.example .env                # и заполнить BOT_TOKEN
```

Создайте базу (однократно):

```bash
psql -U postgres -c "CREATE ROLE tender LOGIN PASSWORD 'tender';"
psql -U postgres -c "CREATE DATABASE tender OWNER tender;"
psql -U postgres -c "CREATE DATABASE tender_test OWNER tender;"   # для тестов
```

Примените миграции и запустите бота:

```bash
alembic upgrade head
python -m app.main
```

Приложение поднимает одновременно long-polling бота и HTTP-сервер:
<http://localhost:8000/health>, <http://localhost:8000/ready>.

Юнит-тесты, парсер-тесты и линтеры работают вообще без базы данных.

## Запуск в Docker

Docker — дополнительный способ развёртывания, а не зависимость разработки.

```bash
cp .env.example .env    # заполнить BOT_TOKEN
docker compose up -d
docker compose logs -f app
```

Поднимаются два сервиса: `postgres` (с healthcheck и именованным томом) и `app`
(ждёт готовности БД, сам применяет миграции через entrypoint, имеет собственный
healthcheck на `/health`). Отключить автоматические миграции: `RUN_MIGRATIONS=false`.

## Миграции

Схема создаётся **только** Alembic-миграциями; `Base.metadata.create_all()`
как стратегия развёртывания не используется.

```bash
alembic upgrade head                      # применить
alembic downgrade base                    # откатить всё
alembic revision --autogenerate -m "..."  # новая миграция
alembic check                             # модели совпадают с миграциями?
```

## Основные Telegram-сценарии

**Создание закупки — пошагово**
`➕ Создать закупку` → `🧩 Пошагово` → название → описание (можно пропустить) →
срок → выбор закупщиков (чекбоксы, «выбрать всех», пагинация) → предпросмотр с
номером `TENDER-2026-000001` → `✅ Опубликовать` → участники получают уведомление.

**Создание закупки — быстро текстом**
`⚡ Быстро текстом` → одно сообщение (`Название:` / `Срок:` / `Описание:` либо
свободный текст «Канцелярия / до 30 августа 17:00 / описание») → парсер
показывает разобранные поля → `✅ Опубликовать` или `👥 Выбрать закупщиков`.
Без подтверждения не публикуется ничего.

**Подача заявки по закупке**
`📢 Активные закупки` → карточка → `➕ Подать заявку` → список товаров одним
сообщением → превью с нумерацией → при необходимости `✏️ Редактировать`,
`🗑 Удалить позицию`, `➕ Добавить позицию`, `💬 Комментарий` → `✅ Отправить`.
Нераспознанные строки не «додумываются», а показываются отдельным блоком.

**Список файлом Excel**
На шаге «отправьте список» вместо текста можно прислать `.xlsx`. Парсер сам
находит строку заголовков (`Наименование` / `Количество` / `Ед. измерения` /
`Комментарий`) в любом порядке колонок, пропускает шапку выгрузки, понимает
`5,5` и `«50 кг»` в одной ячейке, а таблицу без заголовков читает построчно тем
же текстовым парсером. Нераспознанные строки показываются списком ошибок —
ничего не додумывается. Кнопка «📄 Шаблон Excel» выдаёт готовый файл для
заполнения. Ограничения: `MAX_UPLOAD_SIZE_BYTES` и `MAX_UPLOAD_ROWS`; формулы
никогда не вычисляются (`data_only`), XML разбирается через `defusedxml`.

**Своя заявка (инициатива закупщика)**
`➕ Создать заявку` → тема одной строкой → тот же список товаров и то же превью
→ `✅ Отправить`. Заявка уходит сотрудникам тендерного отдела и обрабатывается
обычными статусами: `🟡 В работу`, `✅ Завершить`, `❌ Отклонить` (с причиной).
Одновременно у закупщика может быть только один незавершённый черновик такой
заявки — повторное нажатие переиспользует его, а не плодит пустые записи.

**Обработка заявок**
`📥 Новые заявки` → карточка → `📥 Excel`, `🟡 В работу`, `✅ Завершить`,
`❌ Отклонить` (с обязательной причиной). Закупщик получает уведомление.

**Сводный отчёт**
`📦 Закупки` → карточка закупки → `📊 Сводный Excel`: лист «Заявки» со всеми
позициями всех закупщиков и лист «Сводка» с итогами. Позиции объединяются
только при полном совпадении нормализованного наименования и единицы —
«Масло» и «Масло подсолнечное» останутся раздельно.

Команды `/start`, `/help`, `/cancel` — вспомогательные: всё делается кнопками.

## Безопасность

- Бот закрытый: неизвестный Telegram-аккаунт получает отказ ещё в middleware.
- Идентификация — по числовому `telegram_id`; username кэшируется только для
  отображения и никогда не используется для авторизации.
- RBAC проверяется в сервисном слое при каждом действии, а не скрытием кнопок.
- `callback_data` типизирована: некорректная полезная нагрузка не доходит до
  хендлера, а права всё равно перепроверяются.
- Приглашения одноразовые, с TTL, гасятся под блокировкой строки.
- Защита от Excel formula injection: значения, начинающиеся с `=`, `+`, `-`,
  `@`, таба или CR, экранируются апострофом (`app/domain/text.py`).
- Загружаемые файлы: только `.xlsx`/`.xlsm`, ограничение размера и числа строк,
  чтение в режиме `read_only` + `data_only` (формулы не вычисляются), XML через
  `defusedxml`, имя файла из Telegram никогда не используется как путь.
- Имена файлов санитизируются (кириллица сохраняется, разделители пути и
  зарезервированные имена — нет).
- Ограничены длины ввода, количество позиций, участников и частота сообщений.
- Секреты только в переменных окружения; `.env` в `.gitignore`, токен хранится
  в `SecretStr` и не попадает в логи; audit-payload фильтруется от секретов.
- Структурные логи содержат идентификаторы операций, а не персональные данные.

## Резервное копирование

- Логическая копия: `pg_dump -Fc -U tender tender > tender_$(date +%F).dump`,
  восстановление — `pg_restore -d tender tender_YYYY-MM-DD.dump`.
- В Docker: `docker compose exec -T postgres pg_dump -U tender -Fc tender > backup.dump`.
- Критичные данные не удаляются физически: отзыв доступа — это `is_active=false`
  и `revoked_at`, история статусов и audit log — append-only.
- Excel-файлы генерируются на лету и не хранятся, отдельного бэкапа не требуют.
- Перед обновлением схемы делайте дамп: `alembic downgrade` восстанавливает
  структуру, но не удалённые данные.

## Известные ограничения

1. **FSM хранится в памяти.** Перезапуск процесса сбрасывает незавершённые
   мастера (черновики закупок и заявок в БД сохраняются). Для нескольких
   реплик потребуется `RedisStorage` — точка подключения одна, в `create_dispatcher`.
2. **Один процесс, long polling.** Webhook и горизонтальное масштабирование не
   настроены; FastAPI уже есть и готов принять webhook-роут.
3. **Напоминания — ручные.** Кнопка `🔔 Напомнить` есть, планировщика нет:
   `ProcurementRepository.list_expired_open` — задел под будущий job.
4. **Парсер детерминированный.** Он честно сообщает о нераспознанных строках,
   но не понимает «несколько больших бутылок». Интерфейсы
   `PurchaseListParserProtocol` / `ProcurementParserProtocol` позволяют
   добавить LLM-реализацию, не трогая сервисы.
5. **Редактирование отправленной заявки** не реализовано — по требованиям это
   отдельный контролируемый workflow; сейчас доступны отклонение и повторная
   подача через сотрудника.
6. **Сводный Excel строится в памяти.** Для десятков тысяч позиций это заметная
   нагрузка; при росте объёмов нужен потоковый режим openpyxl.
7. **Одна организация.** Мультиарендность, отделы, поставщики, файлы и
   бюджеты не реализованы, но схема их не блокирует.
8. **Уведомления «best effort».** Если закупщик заблокировал бота, операция
   всё равно сохраняется, а неудача пишется в лог.
